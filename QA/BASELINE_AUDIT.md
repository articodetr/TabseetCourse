## النتيجة التي يمكن الاعتماد عليها

التطبيق يستجيب محليًا عبر IIS Express، وقاعدة الاختبار قابلة للقراءة. **لكن تسجيل الدخول بالحسابات التجريبية فشل فعليًا عبر HTTP، ولذلك لا توجد دورة عمل تعليمية كاملة مثبتة النجاح في هذا التدقيق.** وجود شاشات وأسئلة ونتائج نجاح وشهادات في قاعدة البيانات لا يثبت عملها من واجهة الموقع.

أهم النتائج:

- مخطط جدول أدوار قاعدة البيانات غير متوافق مع الربط الافتراضي لـ ASP.NET Identity المستخدم في التطبيق. محاولات الدخول الخمس فشلت أثناء تحميل الأدوار، رغم صحة كلمات مرور الاختبار.
- طلبات غير مصادق عليها أعادت بيانات محاضرات تتضمن رابط المضيف، وأسئلة اختبار تتضمن مفاتيح التصحيح. بعض إجراءات التعديل أيضًا تفتقد التحقق الخادمي من الدور والملكية وفق مراجعة الكود.
- درجات الاختبارات والواجبات تأتي من المتصفح، والخادم يجمعها بدل تصحيح الإجابات. معادلة التقدير غير صحيحة، وتوليد أرقام الشهادات غير دائم.
- إنشاء Zoom الآلي معطل: `GenerateLectureLink` ترجع `null`. إدخال رابط يدوي لمحاضرة مباشرة ليس مسارًا مستقلًا ناجحًا في التنفيذ الحالي.
- «الدفع عن طريق وكيل» **موجود بالاسم في الواجهة**، لكنه مرتبط بنفس قيمة الدفع المباشر، ولا يوجد حفظ خادمي للطريقة 5. لذلك ليس ميزة مكتملة، وليس مجرد غياب تام للاسم.
- جميع قوالب الشهادات الـ16 المشار إليها في الدورات التجريبية مفقودة من مجلد الصور، مع عيوب إضافية في شروط الإصدار والرقم والصيغة.
- لا يوجد تنفيذ محدد لتسجيل إكمال المدرس للدرس وإشعار الإدارة بذلك. انتهاء الموعد حسابيًا لا يثبت أن المدرس أكمل التدريس.

جرى استخدام HTTP محلي للتحقق من الاستجابات والمصادقة ونقاط القراءة. هذا **ليس اختبار متصفح**: لم يُشغّل JavaScript، ولم تُفحص المحاذاة أو النوافذ المنبثقة أو تحميل الشهادات بصريًا. أعادت أداة المتصفح `No browser is available`، وأعادت مهارة computer-use خطأ `Computer Use native pipe is unavailable ... لم تُختبر جلسات مصادق عليها بعد فشل الدخول، ولم تُزوّر جلسة دخول أو تُعدّل الأدوار لتجاوز العطل. لم تُرسل عمليات إنشاء/تعديل/حذف محتوى أو اعتماد دفع، ولم تُجرَ عملية مالية أو اجتماع Zoom أو رسالة بريد خارجية. خطوات إعادة الإنتاج التي تحتاج كتابة موضحة كخطوات **لاحقة غير منفذة**.

### F01 — عدم توافق Identity يمنع الدخول — P0، صعوبة متوسطة

الملفات: AUTH. يرث `UserIdentityContext` من `IdentityDbContext<MyIdentityUser>` دون تخصيص ربط الأدوار. الجدول الموجود يستعمل أسماء علاقات EDMX بدل `UserId` و`RoleId` التي يتوقعها الربط الافتراضي. مصدر الربط الافتراضي: [Microsoft ASP.NET Identity](https://github.com/aspnet/AspNetIdentity/blob/main/src/Microsoft.AspNet.Identity.EntityFramework/IdentityDbContext.cs).

إعادة الإنتاج المنفذة: افتح `/Home/LogIn`، أرسل حسابًا تجريبيًا مع token صالح، لاحظ الرجوع إلى `MessageID=2` وعدم وجود كوكي مصادقة، ثم راجع `EnsureRolesLoaded` في السجل وقارن أعمدة SQL. تكررت النتيجة للأدوار الثلاثة. رسالة «يجب إضافة إيميل وكلمة مرور» تخفي الاستثناء رغم إرسال الحقلين.

المطلوب لاحقًا: اختيار ربط متوافق بين سياقي Identity وEDMX ومخطط القاعدة، مع الحفاظ على الحسابات والأدوار، وتحسين تسجيل السبب الداخلي ورسالة المستخدم. **لم يُنفذ تغيير مخطط أو Migration.**

### F02 — تفويض نقاط البيانات والتعديل وملكية المدرس — P0، صعوبة مرتفعة

إعادة الإنتاج المنفذة: POST مجهول إلى `AllLectures` أو `LectureByCategorysStd` أعاد روابط المضيف. خطوات لاحقة غير منفذة: دخول المدرس الأول، إرسال تعديل لسؤال/اختبار/محاضرة من الدورة 2، والتحقق من رفض 403 وعدم تغير SQL؛ كذلك طالب ومجهول يحاولان المسارات نفسها. لا يُدَّعى حدوث تعديل غير مصرح به في هذه الجولة.

المطلوب: تفويض افتراضي واضح، فحص ملكية على مستوى المورد في كل إجراء، عدم إعادة Host URL إلا للمخول، تحويل المساعدات إلى خدمات/NonAction. لا يُحل هذا بإخفاء الأزرار.

### F03 — CSRF وعمليات تغيير عبر GET — P0، صعوبة متوسطة

الملفات: `HomeController.cs:928` و`ControlpanelController.cs:776` وبقية POSTs. التحقق من Anti-forgery موجود في تسجيل الدخول، ولم يُعثر عليه في بقية إجراءات الأعمال. `ActiveStudenCourse` يغيّر `std_category_Ispayed` عبر GET؛ التحقق اليدوي من دور المدير لا يعوض CSRF.

إعادة الإنتاج هنا قراءة التوقيع والجسم. لاحقًا: باستخدام جلسة مدير محلية وبسجل تجريبي محدد، اختبر رفض طلب اعتماد بلا token وأي GET يغير الحالة. لم يُنفذ الاعتماد أو هجوم عبر موقع خارجي.

المطلوب: POST محمي بالتفويض وtoken لكل كتابة، معالجة Ajax وإلغاء تغيير الحالة عبر GET. اختبار SameSite إعدادًا وسلوكًا لاحقًا، دون افتراض أنه يغطي كل المسارات.

### F08 — إنشاء Zoom الآلي معطل — P1، صعوبة مرتفعة

الملفات: ZOOM و`CreateLectuer/EditLectuer`. جسم إنشاء JWT وطلب API معلق، والدالة ترجع null. عند وجود مستخدم، ينفذ الكود `lm.Code` مباشرة بعد الاستدعاء، مما يؤدي إلى NullReferenceException؛ إذا لم يوجد مستخدم يرجع رسالة عدم وجود حساب Zoom. لا ينشئ المسار الحالي اجتماعًا.

إعادة الإنتاج هنا قراءة الدالة وتتبع الفرع؛ **لم يُرسل طلب إنشاء محاضرة مباشرة ولم يُنشأ اجتماع خارجي**. مجرد إزالة التعليقات ليست معالجة: نوع JWT القديم متوقف وتوصي Zoom ببدائل OAuth. [إيقاف JWT القديم](https://developers.zoom.us/changelog/platform/jwt-app-type-deprecation/).

المطلوب لاحقًا: فصل الحفظ اليدوي عن توليد الاجتماع، وتصميم ربط حسابات المدرسين عبر OAuth المناسب. التفاصيل في مقارنة طلب العميل أدناه.

### F09 — حفظ الرابط اليدوي لا يعادل تكامل Zoom — P1، صعوبة متوسطة

الملفات: `Views/Teacher/LecturesByCategoryStudend.cshtml:498`، LECTURE، `Teacher/StdonlineCourse.cshtml`. إحدى الواجهات تنفذ `$($(...val())).filter(':first').prop('src')`، أي تتوقع عنصر HTML مثل iframe؛ URL عادي ليس مدخلًا مضمونًا لهذا التحليل. يوجد أيضًا مسار يرسل `LectureLink` بينما النموذج/الحفظ يستعمل `LectureLink_Client`.

فرع المحاضرة المسجلة يحفظ `LectureLink_Client` ويمسح Host/الموعد؛ أما المباشرة فيحاول GenerateLectureLink أولًا، لذلك لا يجوز وصف إدخال Zoom المباشر يدويًا بأنه يعمل. تابع نجاح Ajax في إنشاء المحاضرة يعيد تحميل الصفحة حتى لو رجع `success=false` في HTTP 200، وقد يخفي الخطأ.

إعادة الإنتاج اللاحقة: أدخل رابطًا وهميًا من `example.test` كـURL عادي ثم كنص iframe، وقارن payload والقيمة المحفوظة للمسجل/المباشر دون فتح الرابط. المطلوب: مدخل URL صريح مع تحقق، DTO موحد، ومسار يدوي لا ينادي API.

### Zoom: ثلاث مسائل منفصلة

1. **حساب مجاني:** يمكن للمدرس تنظيم اجتماع بحساب Basic وفق حدود Zoom؛ الاجتماعات الأساسية تخضع عادة لحد 40 دقيقة مع الاستثناءات التي تذكرها الخدمة. هذا قيد خطة لدى Zoom، وليس خللًا يمكن للكود إزالته. [توثيق حدود Basic](https://support.zoom.com/hc/pb/article?id=zm_kb&sysparm_article=KB0059213).
2. **حفظ رابط يدوي:** لا يحتاج إنشاء اجتماع بواسطة API؛ ينشئ المدرس الاجتماع خارج الأكاديمية ثم يحفظ رابط الانضمام. يلزم تطوير مسار الحفظ السليم الحالي؛ ولا يثبت ذلك وجود تكامل API.
3. **إنشاء اجتماع تلقائي:** يحتاج authorization/scopes وربط هوية المضيف. الوثائق الحالية تعرض `POST /users/{userId}/meetings`، وOAuth لتفويض الوصول. اختيار OAuth لحسابات مدرسين مستقلة أو Server-to-Server لحساب أكاديمية واحد قرار معماري لاحق، وليس «تفعيل المجاني» بزر. لم يُفحص حساب Zoom فعلي أو صلاحياته. [Meetings API](https://developers.zoom.us/docs/api/meetings/)، [OAuth](https://developers.zoom.us/docs/integrations/oauth/).
